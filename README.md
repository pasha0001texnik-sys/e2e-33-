# E2E Hub

Платформа для запуска, контроля и разбора E2E-автотестов онбординга, регистрации и входа на собственных тестовых стендах (`dev`, `qa`, `staging`) перед выкаткой релиза.

```
┌──────────────┐   прогоны, статусы, лог     ┌───────────────────────────┐
│  Веб-панель  │ ◄──── Realtime ──────────── │         Supabase          │
│ Next.js      │ ── RLS (роль пользователя) ►│ Postgres · Auth · Vault   │
│ (Vercel)     │                             │ Storage · Realtime        │
└──────┬───────┘                             └─────────────▲─────────────┘
       │ вебхук CI (HMAC)                                  │ service_role
┌──────┴───────┐                             ┌─────────────┴─────────────┐
│   CI / CD    │                             │ Воркеры Playwright        │
└──────────────┘                             │ (Docker на своей VM)      │
                                             │ очередь · cron · cleanup  │
                                             └─────────────┬─────────────┘
                                                           │ только allowlist
                                                  ┌────────▼────────┐
                                                  │ dev / qa / stg  │
                                                  └─────────────────┘
```

| Часть | Где | Что делает |
| --- | --- | --- |
| `apps/web` | Vercel | Панель: запуск прогонов, живой лог, шаги со скриншотами, manual hold, стенды, сюиты, расписания, фикстуры, роли, аудит, вебхук CI, экспорт JSON/CSV |
| `apps/worker` | Docker на любой VM | Берёт прогоны из очереди, гоняет Playwright, пишет шаги/логи/артефакты, планировщик cron, уборщик TTL, очистка фикстур |
| `packages/shared` | — | Типы, защита от production, генерация синтетических данных, маскирование, подпись вебхука |
| `supabase/` | Supabase | Миграции (схема, RLS, RPC очереди, Vault, Realtime, Storage), seed |

Воркер — отдельный процесс, потому что Vercel не держит браузеры и долгие задачи. Очередь живёт в Postgres (`FOR UPDATE SKIP LOCKED`), так что Redis не нужен.

## Запуск

### 1. Supabase

Создайте отдельный проект (не смешивайте с другими приложениями), затем:

```bash
npm i -g supabase
supabase login
supabase link --project-ref <ref>
supabase db push          # применит supabase/migrations
# демо-стенды и сюиты (по желанию): выполните supabase/seed.sql в SQL Editor
```

В **Authentication → URL Configuration** добавьте адрес панели и `https://<панель>/auth/callback` в Redirect URLs.

**Первый зарегистрированный пользователь становится администратором**, остальные — наблюдателями. Роли меняются в разделе «Пользователи».

### 2. Веб-панель на Vercel

1. New Project → импорт репозитория → **Root Directory: `apps/web`** (Vercel сам поставит pnpm-воркспейс).
2. Environment Variables (см. `apps/web/.env.example`):
   - `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (или anon key)
   - `SUPABASE_SERVICE_ROLE_KEY` — только для вебхука CI
   - `CI_WEBHOOK_SECRET` — `openssl rand -hex 32`
3. Deploy.

Локально: `cp apps/web/.env.example apps/web/.env.local`, заполнить, `pnpm install && pnpm dev`.

### 3. Воркер

На любой машине с Docker, у которой есть сетевой доступ к тестовым стендам:

```bash
cp apps/worker/.env.example apps/worker/.env   # SUPABASE_URL + SUPABASE_SERVICE_ROLE_KEY
docker compose up -d --build
docker compose up -d --scale worker=3          # больше воркеров
```

Без Docker: `pnpm --filter @e2e/worker build && npx playwright install chromium && node apps/worker/dist/index.js`.

Воркеров может быть сколько угодно: лимит потоков стенда соблюдается в базе, дубли расписаний отсекаются ключом идемпотентности. По `SIGTERM` воркер перестаёт брать новые прогоны и дожидается текущих.

## Что нужно от тестового стенда

| Что | Зачем | Обязательно |
| --- | --- | --- |
| `GET /health` → `{"env":"qa","build_tag":"v1.42.0"}` | Воркер не стартует, если маркер не совпал, стенд назвал себя `production` или развёрнута другая сборка | Да, для `staging` |
| Перехватчик почты (Mailpit/MailHog) в контуре | Подтверждение email по ссылке или коду | Для сценариев с почтой |
| `POST cleanup API` с `{fixture_id, kind, email, run_id}` и `Authorization: Bearer <cleanup_token>`; 2xx или 404 = удалено | Автоочистка тестовых записей | Желательно |
| `data-testid` на формах (`signup-email`, `login-submit`, …) | Стабильные селекторы | Можно переопределить во флагах стенда |

Полный список селекторов по умолчанию — `apps/worker/src/scenarios/flows.ts`. Пути и селекторы под ваш продукт задаются в карточке стенда, в поле «Флаги»:

```json
{
  "paths": { "signup": "/register", "login": "/sign-in" },
  "selectors": { "login.submit": "button[type=submit]" },
  "password_policy": { "minLength": 12, "symbols": true },
  "keep_fixtures": false
}
```

Секреты стенда (`cleanup_token`, `mailbox_token`) хранятся в Supabase Vault и задаются в карточке стенда. После сохранения значение не показывается.

## Запуск из CI

```bash
E2E_HUB_URL=https://e2e.your.app CI_WEBHOOK_SECRET=... \
  ./scripts/ci-webhook.sh smoke-auth staging "$BUILD_TAG"
```

Подпись — `HMAC-SHA256(secret, "<timestamp>.<body>")` в заголовке `X-E2E-Signature: sha256=<hex>`, время — в `X-E2E-Timestamp`, окно ±5 минут. Повторная доставка с тем же `idempotency_key` возвращает уже созданный прогон. Приоритет CI-прогонов выше плановых.

## Как это защищено

- **Production недостижим по нескольким линиям.** В схеме нет такого окружения. Триггер БД и сервер проверяют, что все URL стенда входят в его allowlist и не пересекаются с таблицей запрещённых хостов. Перед стартом воркер сверяет маркер `/health`. В браузере каждый запрос вне allowlist блокируется, редиректы проверяются вручную (иначе стенд мог бы перенаправить браузер на чужой хост), service workers отключены; если ответ всё же пришёл с чужого хоста, тест немедленно падает с типом `guard`. Серверные запросы воркера (health, почта, cleanup) за редиректами не следуют.
- **Роли через RLS:** наблюдатель только смотрит; QA запускает, ставит на паузу, отменяет и разбирает hold; администратор управляет стендами, сюитами, секретами и ролями. Клиент не может выставить приоритет, ключ идемпотентности или статус прогона.
- **Секреты.** Значения лежат в Vault, их читает только `service_role`. Пароли фикстур хранятся в колонке, недоступной роли `authenticated`. В логах, DOM-снапшотах и экспорте известные секреты вырезаются, на скриншотах поля паролей замазаны. Трейсы Playwright (`TRACE_MODE`) содержат ввод в поля — они лежат в приватном бакете.
- **Аудит** изменений стендов, секретов, сюитов, расписаний, ролей и действий над прогонами.

## Поведение прогонов

- **Ретраи только при сбоях инфраструктуры:** сеть, падение браузера, таймаут навигации. Упавшая проверка не повторяется. Тест, прошедший со второй попытки, помечается **flaky**: прогон остаётся зелёным, но это видно в сводке.
- **Перезапуск упавших** создаёт новый прогон только с упавшими тестами — целиком и со свежими фикстурами.
- **Пауза** останавливает выдачу новых тестов; идущие доходят до конца. **Отмена** прерывает идущие тесты.
- **manual_hold.** Можно поставить галочку «hold при падении» при запуске или нажать «Hold на следующем шаге» у идущего теста. Воркер удерживает браузерную сессию, показывает снимок экрана и ждёт `continue` (повторить шаг), `fail` или `abort`. Таймаут теста на время удержания не тикает. Число одновременных удержаний ограничено настройкой стенда.
- **Фикстуры.** Email вида `e2e+<run>-<n>-<rand>@<тестовый домен стенда>`, пароль по политике стенда. После прогона все фикстуры уходят на очистку через cleanup API. Уборщик раз в минуту отправляет туда же записи с истёкшим TTL и записи умерших прогонов (воркер без heartbeat 5 минут).
- **Тихие часы стенда** задерживают только плановые прогоны; ручные и CI идут всегда.

## Добавить сценарий

1. Опишите `Scenario` в `apps/worker/src/scenarios/index.ts`: шаги через `ctx.step(...)`, данные через `ctx.fixtures.createUser()`, почту через `ctx.mail`.
2. Добавьте ключ и название в `packages/shared/src/scenarios.ts` — тест сверит каталог с реестром воркера.
3. Включите сценарий в сюит в разделе «Сюиты».

## Проверки

```bash
pnpm db:check     # миграции, RLS и права (с дефолтными грантами Supabase), очередь, RPC, уборщик — на PGlite, без Docker
pnpm typecheck
pnpm test         # shared + воркер: фейковый стенд и настоящий Chrome (CHROME_PATH)
pnpm build
```
