# E2E Hub

Платформа для запуска, контроля и разбора E2E-автотестов онбординга, регистрации и входа на собственных тестовых стендах (`dev`, `qa`, `staging`) перед выкаткой релиза.

```
┌──────────────┐   прогоны, статусы, лог     ┌───────────────────────────┐
│  Веб-панель  │ ◄──── Realtime ──────────── │         Supabase          │
│ Next.js      │ ── RLS (роль пользователя) ►│ Postgres · Auth · Vault   │
│ (Vercel)     │                             │ Storage · Realtime        │
└──────┬───────┘                             └─────────────▲─────────────┘
       │ вебхук CI (HMAC)                                  │ service_role
┌──────┴───────┐                             ┌─────────────┴─────────────┐
│   CI / CD    │                             │ Воркеры Playwright        │
└──────────────┘                             │ (Docker на своей VM)      │
                                             │ очередь · cron · cleanup  │
                                             └─────────────┬─────────────┘
                                                           │ только allowlist
                                                  ┌────────▼────────┐
                                                  │ dev / qa / stg  │
                                                  └─────────────────┘
```

| Часть | Где | Что делает |
| --- | --- | --- |
| `apps/web` | Vercel | Панель: запуск прогонов, живой лог, шаги со скриншотами, manual hold, стенды, сюиты, расписания, фикстуры, роли, аудит, вебхук CI, экспорт JSON/CSV |
| `apps/worker` | Docker на любой VM | Берёт прогоны из очереди, гоняет Playwright (web) или Appium (android/ios), пишет шаги/логи/артефакты, планировщик cron, уборщик TTL, очистка фикстур |
| `packages/shared` | — | Типы, защита от production, генерация синтетических данных, маскирование, подпись вебхука |
| `supabase/` | Supabase | Миграции (схема, RLS, RPC очереди, Vault, Realtime, Storage), seed |

Воркер — отдельный процесс, потому что Vercel не держит браузеры и долгие задачи. Очередь живёт в Postgres (`FOR UPDATE SKIP LOCKED`), так что Redis не нужен.

## Запуск

### 1. Supabase

Создайте отдельный проект (не смешивайте с другими приложениями), затем:

```bash
npm i -g supabase
supabase login
supabase link --project-ref <ref>
supabase db push          # применит supabase/migrations
# демо-стенды и сюиты (по желанию): выполните supabase/seed.sql в SQL Editor
```

Без CLI: выполните файлы из `supabase/migrations` по порядку в **SQL Editor**. Если позже перейдёте на CLI, сначала отметьте их применёнными: `supabase migration repair --status applied <версия>` для каждого файла.

**Обновление уже развёрнутой базы:** при появлении нового файла в `supabase/migrations` выполните только его (например, `20261122000003_stage3.sql` — мобильные стенды и зависимости тестов).

В **Authentication → URL Configuration** добавьте адрес панели и `https://<панель>/auth/callback` в Redirect URLs.

**Первый зарегистрированный пользователь становится администратором**, остальные — наблюдателями. Роли меняются в разделе «Пользователи».

### 2. Веб-панель на Vercel

1. New Project → импорт репозитория → **Root Directory: `apps/web`** (Vercel сам поставит pnpm-воркспейс).
2. Environment Variables (см. `apps/web/.env.example`):
   - `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (или anon key)
   - `SUPABASE_SERVICE_ROLE_KEY` — только для вебхука CI
   - `CI_WEBHOOK_SECRET` — `openssl rand -hex 32`
3. Deploy.

Локально: `cp apps/web/.env.example apps/web/.env.local`, заполнить, `pnpm install && pnpm dev`.

### 3. Воркер

На любой машине с Docker, у которой есть сетевой доступ к тестовым стендам:

```bash
cp apps/worker/.env.example apps/worker/.env   # SUPABASE_URL + SUPABASE_SERVICE_ROLE_KEY
docker compose up -d --build
docker compose up -d --scale worker=3          # больше воркеров
```

Без Docker: `pnpm --filter @e2e/worker build && npx playwright install chromium && node apps/worker/dist/index.js`.

Воркеров может быть сколько угодно: лимит потоков стенда соблюдается в базе, дубли расписаний отсекаются ключом идемпотентности. По `SIGTERM` воркер перестаёт брать новые прогоны и дожидается текущих.

### 4. Мобильные стенды (по желанию)

Стенд с платформой `android` или `ios` воркер гоняет через [Appium](https://appium.io): сервер Appium с эмулятором или устройством запускается отдельно (Android — Linux с KVM или любой ПК с Android Studio; iOS — только macOS с Xcode), его адрес указывается у стенда (`appium_url`), сборка приложения и устройство — в `capabilities`:

```json
{
  "appium:deviceName": "emulator-5554",
  "appium:app": "/apps/app-qa.apk",
  "appium:appPackage": "com.example.app"
}
```

Мобильный воркер — тот же образ с `WORKER_PLATFORMS=android,ios`: `docker compose --profile mobile up -d`. Каждая попытка теста открывает новую Appium-сессию с чистым состоянием приложения (`appium:noReset: false`, можно переопределить в capabilities).

Селекторы по умолчанию — accessibility id (`~signup-email`, `~login-submit` …; в React Native это `testID`), список — `apps/worker/src/scenarios/mobile.ts`; переопределяются во флагах стенда ключами `mobile.<ключ>` или `<ключ>`. Подтверждение почты — кодом из письма, если на экране есть поле кода, иначе диплинком из письма.

Ограничение: сетевой трафик нативного приложения воркер не перехватывает, поэтому allowlist для мобильных стендов проверяется только у URL стенда, а защиту от production дают сборка приложения под тестовый контур и маркер `/health`.

## Что нужно от тестового стенда

| Что | Зачем | Обязательно |
| --- | --- | --- |
| `GET /health` → `{"env":"qa","build_tag":"v1.42.0"}` | Воркер не стартует, если маркер не совпал, стенд назвал себя `production` или развёрнута другая сборка | Да, для `staging` |
| Перехватчик почты (Mailpit/MailHog) в контуре | Подтверждение email по ссылке или коду | Для сценариев с почтой |
| HTTP-источник кодов в контуре (перехватчик SMS, вебхук-синк) | Проверочный код для сценария из `ctx.codes` | Для сценариев с кодом не из почты |
| `POST cleanup API` с `{fixture_id, kind, email, run_id}` и `Authorization: Bearer <cleanup_token>`; 2xx или 404 = удалено | Автоочистка тестовых записей | Желательно |
| `data-testid` на формах (`signup-email`, `login-submit`, …) | Стабильные селекторы | Можно переопределить во флагах стенда |
| Логирование заголовка `X-E2E-Trace-Id` | Сквозная трассировка: тот же `trace_id`, что в панели и логах воркера | Желательно |

Полный список селекторов по умолчанию — `apps/worker/src/scenarios/flows.ts`. Пути и селекторы под ваш продукт задаются в карточке стенда, в поле «Флаги»:

```json
{
  "paths": { "signup": "/register", "login": "/sign-in" },
  "selectors": { "login.submit": "button[type=submit]" },
  "password_policy": { "minLength": 12, "symbols": true },
  "keep_fixtures": false
}
```

**Источник кодов (`code_provider`)** — универсальный адаптер получения проверочного кода из HTTP-источника **внутри тестового контура** (перехватчик SMS, вебхук-синк): сценарий вызывает `ctx.codes.waitForCode(id)` (id — телефон/email/request-id), код извлекается по полю JSON или регэкспу. Настраивается в карточке стенда отдельной секцией «Источник кодов» (URL, путь/метод, имя секрета в Vault, правило извлечения, таймауты, release-эндпоинт) — форма валидирует хост против `allowed_hosts`/`forbidden_hosts` и запрещает абсолютные пути, так что источник остаётся сервисом контура (внешние OTP/SMS-сервисы не используются; запрос идёт с `redirect:"manual"` и таймаутом). Таймаут/ошибка фиксируются в результате прогона (`run_tests.error_kind`, `run_results.error`); незакрытый запрос освобождается через `release_path` при завершении или падении шага. Готовый сквозной пример — сценарий `e2e.full-signup` (регистрация → код → вход).

Секреты стенда (`cleanup_token`, `mailbox_token`, при необходимости `codes_token`) хранятся в Supabase Vault и задаются в карточке стенда. После сохранения значение не показывается.

## Трассировка

У каждого прогона есть `trace_id` (виден в панели). Воркер пишет его в каждую строку своего лога и добавляет ко всем запросам на стенд — из браузера и серверным (health, почта, cleanup):

| Заголовок | Значение |
| --- | --- |
| `X-E2E-Trace-Id` | `trace_id` прогона |
| `X-E2E-Run-Id` | id прогона |
| `X-E2E-Test-Id` | id теста (запросы из браузера) |
| `traceparent` | W3C Trace Context с тем же trace id — подхватят OpenTelemetry-совместимые стенды; если приложение ставит свой `traceparent`, он не перезаписывается |

Заголовки добавляются на сетевом уровне, поэтому CORS-preflight на стенде не появляется. Найти события стенда по прогону: поиск по `X-E2E-Trace-Id` в логах стенда.

## Запуск из CI

```bash
E2E_HUB_URL=https://e2e.your.app CI_WEBHOOK_SECRET=... \
  ./scripts/ci-webhook.sh smoke-auth staging "$BUILD_TAG"
```

Подпись — `HMAC-SHA256(secret, "<timestamp>.<body>")` в заголовке `X-E2E-Signature: sha256=<hex>`, время — в `X-E2E-Timestamp`, окно ±5 минут. Повторная доставка с тем же `idempotency_key` возвращает уже созданный прогон. Приоритет CI-прогонов выше плановых.

## Как это защищено

- **Production недостижим по нескольким линиям.** В схеме нет такого окружения. Триггер БД и сервер проверяют, что все URL стенда входят в его allowlist и не пересекаются с таблицей запрещённых хостов. Перед стартом воркер сверяет маркер `/health`. В браузере каждый запрос вне allowlist блокируется, редиректы проверяются вручную (иначе стенд мог бы перенаправить браузер на чужой хост), service workers отключены; если ответ всё же пришёл с чужого хоста, тест немедленно падает с типом `guard`. Серверные запросы воркера (health, почта, cleanup) за редиректами не следуют.
- **Роли через RLS:** наблюдатель только смотрит; QA запускает, ставит на паузу, отменяет и разбирает hold; администратор управляет стендами, сюитами, секретами и ролями. Клиент не может выставить приоритет, ключ идемпотентности или статус прогона.
- **Секреты.** Значения лежат в Vault, их читает только `service_role`. Пароли фикстур хранятся в колонке, недоступной роли `authenticated`. В логах, DOM-снапшотах и экспорте известные секреты вырезаются, на скриншотах поля паролей замазаны. Трейсы Playwright (`TRACE_MODE`) содержат ввод в поля — они лежат в приватном бакете.
- **Аудит** изменений стендов, секретов, сюитов, расписаний, ролей и действий над прогонами.

## Поведение прогонов

- **Ретраи только при сбоях инфраструктуры:** сеть, падение браузера, таймаут навигации. Упавшая проверка не повторяется. Тест, прошедший со второй попытки, помечается **flaky**: прогон остаётся зелёным, но это видно в сводке.
- **Перезапуск упавших** создаёт новый прогон только с упавшими тестами — целиком и со свежими фикстурами.
- **Пауза** останавливает выдачу новых тестов; идущие доходят до конца. **Отмена** прерывает идущие тесты.
- **manual_hold.** Можно поставить галочку «hold при падении» при запуске или нажать «Hold на следующем шаге» у идущего теста. Воркер удерживает браузерную сессию, показывает снимок экрана и ждёт `continue` (повторить шаг), `fail` или `abort`. Таймаут теста на время удержания не тикает. Число одновременных удержаний ограничено настройкой стенда.
- **Фикстуры.** Email вида `e2e+<run>-<n>-<rand>@<тестовый домен стенда>`, пароль по политике стенда. После прогона все фикстуры уходят на очистку через cleanup API. Уборщик раз в минуту отправляет туда же записи с истёкшим TTL и записи умерших прогонов (воркер без heartbeat 5 минут).
- **Тихие часы стенда** задерживают только плановые прогоны; ручные и CI идут всегда.
- **Гео- и сетевая эмуляция.** Профиль выбирается в форме запуска (`net_profile`) или задаётся по умолчанию на стенде через `test_flags.net_profile` (прогон переопределяет стенд). Пресеты (`@e2e/shared` `NET_PROFILES`): `none` (без эмуляции), `offline`, `slow-3g`, `fast-3g`, `geo-moscow`/`geo-berlin`/`geo-newyork`. Эмуляция только в контексте браузера воркера: координаты и разрешение geolocation, троттлинг скорости/задержки и offline через CDP **поверх** перехвата запросов — allowlist и проверка редиректов не меняются, трафик никуда не маршрутизируется. Применённый профиль, координаты/регион и параметры сети пишутся в `run_results.network_profile`/`region` и попадают в отчёт и экспорт. Для нативных мобильных стендов сетевая эмуляция браузера не применяется.
- **Многошаговые сценарии.** Сценарий может объявить `dependsOn` — он стартует только после успеха зависимостей и получает их данные (например, подтверждённого пользователя). Если зависимость упала, зависимые тесты пропускаются с причиной. Зависимости подтягиваются автоматически: в сюит и при перезапуске упавших. Пример цепочки: `signup.verify-email` → `onboarding.profile` → `login.after-onboarding` — регистрация, онбординг и повторный вход на одном и том же пользователе.

## Добавить сценарий

1. Опишите `Scenario` в `apps/worker/src/scenarios/index.ts`: шаги через `ctx.step(...)`, данные через `ctx.fixtures.createUser()`, почту через `ctx.mail`. Реализация для web — `run`, для мобильных стендов — `runMobile`.
2. Передача данных между тестами: в сценарии-поставщике `ctx.share("user", user.id)`, в зависимом — `dependsOn: ["…"]` и `ctx.fromDependency("…", "user")` (+ `ctx.fixtures.adopt(id)` для фикстуры). Передавайте только id и несекретные значения — они видны в панели.
3. Добавьте ключ, название, `dependsOn` и платформы в `packages/shared/src/scenarios.ts` — тест сверит каталог с реестром воркера.
4. Включите сценарий в сюит в разделе «Сюиты».

## Соответствие ТЗ

| Этап | Сделано |
| --- | --- |
| 1 · MVP | Панель, очередь, воркер Playwright, генератор фикстур, реестр, логи и скриншоты. По итогам ревью сюда же добавлены защита от production, RBAC, Vault, ручная очистка и TTL-уборщик |
| 2 · CI/CD и диагностика | Вебхук CI с HMAC и идемпотентностью, лимиты потоков по стендам, manual_hold, автоочистка фикстур, расписания с политикой перекрытия |
| 3 · Расширение | Горизонтальное масштабирование воркеров, мобильные стенды через Appium (отдельный тип воркера и очередь по платформам), многошаговые сценарии с передачей фикстур между тестами (`dependsOn`) |

Отличия от исходного текста ТЗ (согласованы при ревью):

- **Стек:** вместо FastAPI/NestJS + Redis + Celery/BullMQ — Next.js (Vercel) + Supabase; очередь в Postgres. Меньше сервисов, тот же функционал: приоритеты, лимиты, таймауты, повторы.
- **«Перезапустить упавшие шаги»** реализовано как перезапуск упавших **тестов** целиком со свежими фикстурами: шаг E2E без предыдущих шагов не воспроизводим.
- **manual_hold** показывает снимок экрана на момент удержания; живой трансляции браузера нет.
